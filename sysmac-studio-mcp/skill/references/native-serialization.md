# 原生序列化与「假 0 错」离线预检

> 本文件是跨工程可移植知识，不含任何本机路径、工程名、实体 GUID 或窗口句柄。

## 1. 最隐蔽的失败模式：编译确实跑了，但源码根本没进内存

离线改写梯图段文件（`PouBody` 的 XML）后，经常出现这样的假象：

1. `json.loads` 通过、`zipfile.testzip()` 为 `None`、`ss_verify.py` 报 `PASS`；
2. 工程能打开，`检查所有程序` / 编译按钮都有忙碌生命周期，面板出现大量既有警告；
3. 编译结果却是 **0 错误**，连故意埋下的未定义标识符也查不出来；
4. 随后原生保存，段文件里的程序体变成 `{"CLs":[],"RRI":1,"VLs":[]}`。

根因几乎总是**段文件的 JSON 序列化风格不符合 Sysmac 原生格式**，加载器静默拒绝，内存里的程序体退化为空梯图。0 错不代表程序正确，只代表空程序当然没有错误。

## 2. 原生格式规范

| 项 | Sysmac 原生（可用） | Python `json.dumps`（被拒绝） |
| --- | --- | --- |
| 文件开头 | UTF-8 BOM | 无（除非手工补） |
| ST 文本内换行转义 | `\u000d\u000a` | `\r\n` 短转义 |
| 文件结尾 | **一个 CRLF** | 无 |
| 数值/键顺序 | 原生序列化器决定，不要重排 | 整包 `dumps` 会改变浮点表示与键顺序 |

改 `TXT` 时优先做**字节级替换**已转义的字符串值，不要整包 `json.dumps` 重写；否则会同时改掉风格、键顺序、浮点表示并丢掉结尾 CRLF。

## 3. 离线预检：`ss_fmtcheck.py`

在把工程交给 Sysmac 之前先跑一次离线检查：

```text
python skill/scripts/ss_fmtcheck.py check <归档路径> [--verbose]
```

它遍历归档中所有像梯图段文件的 XML，逐项判定 BOM、换行转义风格、结尾 CRLF、ST 的 CRLF/裸 LF/行数、是否残留临时探针，任一项不合格即 `RESULT=FAIL`。这补上了 `ss_verify.py` 的盲区：后者只查 ZIP / 实体伴生文件，不解析段文件序列化风格。

归档对比用：

```text
python skill/scripts/ss_fmtcheck.py diff <前> <后> [--body <PouBody 条目名>] [--axis <轴条目名>]
```

## 4. 判定「本轮真的编译过」

以下两种证据取其一即可，**不要加码**：

- 观察到忙碌状态（StatusBar / ProgressBar、按钮先禁用后恢复）；或
- 编译前后计数 / 消息网格快照发生变化（例如 `(0,0) → (0,N)`）。

判定脚本若额外强制「必须观察到忙碌」，可能因为检查命令比轮询更快结束而误报 `INCONCLUSIVE`——**判定条件不能比规则更严**。

同时必须做阳性对照：故意埋一个未定义标识符，确认它能被报出来。只在不加探针的干净版上看到 0 错，不算验证通过。

## 5. 错误跟踪日志是硬判据

编译 / 保存前后对照错误跟踪日志字节增量。出现段文件加载异常（反序列化 / 根级别数据无效）就说明程序体没加载，此时一切 0 错结论立即作废。日志增量 0 是「程序体真的进了内存」的必要条件。

## 6. 原生保存后的归档对比：先归一化 GUID

原生保存会轮换顶层 `.oem` GUID，并把该 GUID 用在目录名与若干顶层文件名里。直接比条目名会得到「整包全增全删」的假差异。正确做法：

1. 从 `.oem` 条目解析顶层 GUID；
2. 剥掉 `<GUID>/` 目录前缀，以及顶层 `<GUID>.` 文件名前缀；
3. 再比对条目集合与内容。

按此归一化后，关键文件（梯图段、轴配置）应逐字相同；正常的净变化只有 GUID 轮换、新增编译结果实体、以及少数元数据 / 编译产物被重生成。**条目数会变，不要硬编码。**

## 7. ESI 核对框的出现时机

打开工程时若机器安装的 ESI 与工程内记录不同，会弹核对框。它通常在「正在打开工程」进度框**之后**才出现；过早点击会找不到按钮。先轮询窗口状态与弹层列表，确认核对框确实出现后再选择保留工程内 ESI 的按钮。不要为了消除弹框而选择用新装 ESI 覆盖工程的选项——那会污染受控实验。
